01 — THE PACKAGE

One folder is the device.

Hover the files. Each entry lights up the part of the physical twin it describes — the front panel you see was compiled in your browser from model/device-model.json: terminals, mounting, display, indicators. No vendor artwork was shipped.

@example/pump-controller v1.0.0
├── open-device.json # identity · artifacts · digests
├── model/device-model.json # ports · terminals · mounting · display → SVG
├── views/front-panel.html # sandboxed HTML + CSS
├── logic/program.fbdbin # + fbd-runtime.wasm (pinned)
├── scenarios/ # portable conformance tests
└── evidence/ # bound to exact published bytes

The format describes what a device is. Your platform decides how instances connect, who may control them, and how programs reach real hardware.

03 — TRUST BOUNDARY

Open format. Explicit authority.

Open Device defines

  • manifest and schemas
  • port and signal types
  • HTML/CSS view protocol
  • Wasm runtime ABI
  • scenario and evidence formats
  • package resolution

Your platform decides

  • authentication and authorization
  • live protocol drivers
  • telemetry storage
  • controller deployment
  • activation and rollback
  • product-specific editors

Vendor views run in a browser sandbox and emit intent — not hardware commands.

Help define a portable device package.

We are building the first narrow vertical slice in public. Manufacturers, industrial developers, runtime authors, and web tooling contributors are invited to challenge the model with real equipment.
